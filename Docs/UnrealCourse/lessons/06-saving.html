Station UE 06

Saving

Progress is one small JSON file, written on every change and built to survive a crash mid-write and a damaged file. You port the format and the file store, and move the headset's own settings from PlayerPrefs to Unreal config.

At the end
save.json on the headset in the same format Unity writes, a file store that swaps in atomically, and preferences that survive a restart.
On the headset
Complete a level with console commands, kill the app, start it again: the next level is unlocked.
Unity equivalent
Milestone M9, "JSON save with auto-save".

The format

Rules the reader follows, from SaveJson.cs:

  • Keys are written sorted, so two saves with the same content are the same text.
  • Any well-formed JSON is accepted and unknown members are ignored.
  • A bad entry under bestTimes fails the whole file. Unlocking is derived from best times, so a half-read set would silently lock levels.
  • A bad entry under stars or inProgress is skipped. Neither may cost the player their best times.
  • A version 1 file has no stars. It loads, AwardMissingStars fills the stars in from each level's thresholds, and the next write is version 2.

Docs driftCLAUDE.md still shows the version 1 format. The code is at version 2. Port the code.

Unreal concepts

Files and paths

FPaths names the engine's folders; FFileHelper reads and writes whole files; IFileManager moves and deletes them. All three are in the Core module, so the file store can stay in TsugiCore.

FPaths::ProjectSavedDir() is the equivalent of Application.persistentDataPath: the per-app writable folder on every platform.

The Json module

Unreal has a JSON reader and writer in the Json module, which depends only on Core. Add it to TsugiCore.Build.cs. You get a DOM of FJsonObject and FJsonValue, which replaces the 250-line hand-written parser in the C#. That parser existed only because Core could not reference Unity's JSON.

USaveGame, and why this port does not use it

The usual Unreal way to save is a USaveGame subclass with UPROPERTY fields, written with UGameplayStatics::SaveGameToSlot. It is binary, versioned by the engine, and needs almost no code. If you were starting fresh you would probably use it.

Here the format is a contract. It is pinned by tests, it is readable when a tester sends you their file, and the reader's tolerance rules are deliberate. Keeping it means 40 test cases come across and behaviour stays identical. Know that USaveGame exists; you will meet it in every other Unreal project.

Config

Settings that belong to the device, such as which hand is dominant, are not progress. Unity kept them in PlayerPrefs. Unreal's equivalent is the config system: .ini files layered from engine defaults down to a per-user file. GConfig reads and writes them, and GGameUserSettingsIni names the per-user file that survives updates.

Steps

  1. Port the writer by hand. The module's own writer would work, but writing the text yourself keeps the key order and the layout exactly as the tests expect.

    One real differenceC# writes doubles with the round-trip format, so 12 seconds is 12. FString::SanitizeFloat writes 12.0. Both are valid JSON and each side reads the other's file. A Unity test that compares exact text for a whole number will need its expected string changed; a test that reads back what it wrote will not.

  2. Port the reader on the Json module. The skeleton shows the two different tolerance rules.

    Check in your engineThe FJsonObject accessors changed their string parameter types across 5.x releases. If a call does not compile, read Dom/JsonObject.h and use what it declares.

  3. Port the file store. The write is the part that matters. A crash between the two steps leaves either the old file or the new one, never half of one.

    The C# takes an Action<string> for logging so Core does not depend on Unity's logger. In Unreal, logging is in Core, so Log can simply be UE_LOG with a category you declare in TsugiCore.

  4. Switch the subsystem to the file store. One line changes in UTsugiGameSubsystem::Initialize:

    Read that log line on the headset and write the path into BUILDING.md. You will want to pull the file off the device when testing.

    Not confirmedWhere ProjectSavedDir lands on Quest depends on an Android project setting about using the external files directory. The Unity build writes under /sdcard/Android/data/<package>/files/. Do not assume the Unreal path; log it.

  5. Port the preferences. XRPreferences and its in-memory store go to TsugiCore unchanged in shape. The device store goes to TsugiXR and writes config.

    Keep the four key names from the C# (tsugi.xr.dominantHand and so on). Create the preferences in the subsystem beside the flow and expose them with a getter.

  6. Save at the same moments Unity does. For now, add a Tsugi.Save console command. The real triggers arrive with the systems that raise them: after every board change (lesson 11), on entering Pause (lesson 14) and when the app loses focus or is suspended (lesson 14).

Acceptance checks

  • All tests under Tsugi.Core.SaveJson, FileSaveStore, StarsAndSave and Preferences pass.
  • A save.json copied from a Unity build loads in the Unreal build with the same best times and stars.
  • A version 1 file loads, gains stars, and is written back as version 2.
  • Replacing save.json with { broken and starting the game produces save.json.corrupt and a fresh save, with one warning in the log.
  • On the headset: complete level 0 by console, force-stop the app, relaunch; level 1 starts.
  • On the headset: a preference written by console survives a relaunch.

Pitfalls

  • A byte-order mark. Unity writes UTF-8 without a BOM. Ask SaveStringToFile for the same, as the code above does, or a file written by one engine may be refused by the other's strict reader.
  • Writing on every change is deliberate. The file is a few kilobytes. Do not batch or delay writes to "optimise" them: a headset can be taken off and the app killed at any moment.
  • Restoring a board. A saved attempt is applied with SetUnchecked, never by replaying TryPlace. Replaying in raster order can refuse a board that is perfectly legal, because legality depends on what was already there.
  • Nothing XR-only goes in save.json. Decision X1 in the XR spec. The anchor id, the cell size and the dominant hand live in preferences.

Knowledge check

The file has a valid bestTimes block and one entry in inProgress whose key is "XX". What does the reader do?

  • Rejects the file and sets it aside as corrupt.
  • Loads the best times and skips that in-progress entry.
  • Loads the entry with a default key.

An unfinished attempt is worth less than the player's record. Only a bad best time, which unlocking depends on, fails the file.

Why write to save.json.tmp and then move it over save.json?

  • It is faster than writing in place.
  • If the app dies during the write, the previous save is still intact.
  • Android does not allow overwriting files.

Writing in place truncates the file first. A crash at that moment leaves an empty save.

Where does the dominant-hand setting belong?

  • In save.json, with the rest of the player's data.
  • In per-user config, through the preference store.
  • In a data asset.

It belongs to the device and the person wearing it, not to puzzle progress. Data assets are read-only content shipped in the build.
