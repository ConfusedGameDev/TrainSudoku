Performance on Quest

A standalone headset is a phone strapped to your face, drawing every frame twice. This lesson has no Unity code to port: the Unity project left this work for a milestone it has not started. You set a target, measure against it, and learn what Unreal's mobile renderer costs and why.

At the end
A written frame budget, a repeatable measurement, and a build that holds its refresh rate on both target devices.
On the headset
90 Hz on Quest 3 and never under 72 on Quest 3S, through the busiest moment of the game.
Unity equivalent
Milestone XR11, not started. The targets come from Docs/XR-PRD.md.

The target

Refresh rateTime per frameUse
72 Hz13.9 msThe default, and the floor on Quest 3S
90 Hz11.1 msThe target on Quest 3
120 Hz8.3 msNot a goal for this game

The store's rule, VRC.Quest.Performance.1: the app must run at an allowed refresh rate and hold a rendering rate of at least 60 frames per second. Meta tests by running the app for up to 45 minutes with the OVR Metrics Tool and looking for extended periods below that. Loading screens are exempt.

That floor is not your target. A missed frame in a headset is felt as a judder of the whole world, and in passthrough the real room keeps moving smoothly while your board stutters against it. Aim to render every frame at the display's rate.

Unreal concepts

The mobile renderer

On Android, Unreal uses a different renderer from desktop. The settings that matter for a headset:

SettingValueWhy
Shading pathMobile forwardOne pass per object with lighting computed in it. Required for MSAA.
Mobile HDROffHDR adds a full-screen pass and disables hardware MSAA resolve. No post-processing with it off, which this game does not need.
Anti-aliasingMSAA 4×Nearly free on tile-based mobile GPUs, and thin rails need it.
Mobile Multi-ViewOnBoth eyes drawn in one pass. The equivalent of Unity's single-pass instanced.
Graphics APIVulkan onlyThe supported API for Quest, and required for foveation.
Foveated renderingStart at High, dynamic onFewer pixels shaded at the edge of the lens, where they are not seen clearly.

The Meta XR Project Setup Tool from lesson 1 set most of these. Open it again now and read each rule it lists, so you know what it changed.

Where the time goes

A frame has two budgets that run in parallel, and the slower one sets the frame rate.

  • CPU. The game thread runs your Ticks. The render thread turns visible objects into draw calls. The number of draw calls is usually what limits it.
  • GPU. Vertices to transform, and pixels to shade. On mobile the pixel cost dominates, and anything translucent is the most expensive kind of pixel because it is shaded on top of what is already there.

Steps

  1. Write the budget down. Before measuring, state what you expect. Fill in this table for an 8×8 board with a full solution, during the train run, with both hands tracked and the wrist menu open. It is the worst case.

    ThingCountDraw callsNote
    Slabs641Instanced, lesson 7
    Track piecesup to about 40one each, todayCandidates for instancing by key: six components
    Clue signs16 poles, 16 numerals32Poles can be instanced
    Tunnels2a few
    Train cars88 or moreDepends on materials per car
    Tray6 pieces6Hidden during the train
    Signboard, wrist panel, roundel3 widgets3Translucent, and each is a render target
    Hands22
    Handle, shadow catcher2 or 3Shadow catcher is large and translucent

    A widely used working limit for Quest is a few hundred draw calls and several hundred thousand triangles per frame, with Quest 3 comfortably above Quest 3S. This game should sit far below both. If your measured numbers are several times your table, something is being drawn that you did not plan.

  2. Build a repeatable test. Performance work without a fixed scenario is guesswork. Add a console command, Tsugi.Bench, that loads the largest shipped board, fills it from the solver, and runs the train in a loop. Always measure a Development or Shipping build on the device, never the editor and never over Link.

  3. Take a baseline. Install OVR Metrics Tool. Run the benchmark for five minutes on each device at 72 Hz. Record average frame rate, stale frame count, and CPU and GPU utilisation. Save the log. Every later change is judged against this file.

  4. Set the refresh rate. The default is 72 Hz on every device. Ask for 90 on Quest 3 only.

    Meta's plugin provides three Blueprint nodes: Get Available Display Frequencies, Get Current Display Frequency and Set Display Frequency. Call them from BP_TsugiPawn at start, after reading the device type: if the device is a Quest 3 and 90 is in the available list, set 90; otherwise leave 72. The supported devices in the Meta XR settings must be listed for non-default rates to be offered.

    From the Unity buildQuest 3's device codename is eureka. A check for the string "quest3" misses it. Use the plugin's device-type enum, not a name match.

  5. Set foveation. In Project Settings > Plugins > Meta XR > Mobile: Foveated Rendering Level to High and Dynamic Foveated Rendering on. Dynamic means the system raises foveation only when the GPU is busy, up to your maximum.

    Known issueMeta's release notes for plugin 207 list: "Changing Fixed Foveated Rendering settings at runtime is not supported on UE 5.7+". Set it in project settings and do not build a feature that changes it during play. The same notes say Dynamic Resolution is only available on Meta's engine fork.

    Look at the board's far edge and the signboard text with foveation at High. If text at the edge of your view shimmers, drop to Medium.

  6. Check render scale. The Unity build renders at 0.8 scale, which nobody recorded in its docs. The store recommends at least 85% render scaling for most of the experience (VRC.Quest.Performance.4). Start at 1.0. Lower it only if you cannot hold frame rate any other way, and not below 0.85.

  7. Find the real cost. Run the benchmark at the target rate with stat unit. Then act on what it says, and only that:

    What is slowLook atLikely fixes in this game
    Game threadUnreal Insights, your Tick functionsSigns facing the head every frame for all 16 clue signs; the grab component measuring distance to 64 volumes per hand. Do the first only when the head has moved; narrow the second to the cells near the hand.
    Render threadstat scenerendering: draw callsInstance track pieces by key. Instance clue poles. Merge the train's materials.
    GPURenderDoc; turn things off one at a timeThe shadow catcher and widget panels are large translucent surfaces. Shadows from a movable light are costly: the Unity build uses one cascade, 2.5 m range. Widget components redrawing every frame: make sure manual redraw from lesson 12 is on.

    Change one thing, run the benchmark, compare with the baseline log, and keep or revert. Write each result down, including the ones that made no difference.

  8. Watch the heat. A headset that runs hot lowers its own clock speed after some minutes, and a game that held 90 at minute one drops frames at minute twenty. In the Meta XR settings, the suggested CPU and GPU performance levels default to sustained levels; leave them there. Run the benchmark for the full 45 minutes at least once.

  9. Revisit occlusion. If your team chose hand masking in lesson 10, measure it now: it should be nearly free. If the team wants depth-based occlusion, this is the lesson to price it, with the benchmark, before anyone commits to an engine fork.

Your work

  • The Tsugi.Bench command.
  • A short PERFORMANCE.md: the budget table with your measured numbers beside the expected ones, the baseline, each change and its effect, and the final figures for both devices.
  • Refresh rate selection per device.
  • Whatever the measurements say needs fixing, and nothing they do not.

Acceptance checks

  • PERFORMANCE.md has a budget, a baseline and a final measurement for Quest 3 and for Quest 3S.
  • On Quest 3 the benchmark holds 90 frames per second for five minutes with no more than a handful of stale frames.
  • On Quest 3S the benchmark holds 72 with the same.
  • A 45-minute run on one device shows no extended period below 60 in the OVR Metrics log.
  • Loading a level causes no visible hitch: track meshes are baked, not generated.
  • Render scale is 0.85 or higher.
  • Signboard text is sharp where I look at it, with foveation on.
  • I can name the single most expensive thing in the frame and how I know.

Pitfalls

  • Optimising in the editor. The desktop renderer and a desktop GPU tell you nothing about a mobile tile-based GPU. Only the device counts.
  • Development builds are slower. They carry logging and checks. Compare like with like, and take the final numbers from a Shipping build.
  • Per-frame logging. A log line every frame costs real time on Android, and floods the buffer you read logs from. Remove them before measuring.
  • Garbage collection hitches. Creating and destroying components every time a piece is placed produces garbage. If you see a periodic spike, pool the held piece, the ghost and the falling pieces.
  • Fixing what is not slow. Instancing forty track pieces is satisfying and may change nothing if the GPU is the limit. Measure first.

Knowledge check

stat unit shows Game 4 ms, Draw 5 ms, GPU 15 ms at a 90 Hz target. Where do you look first?

  • Your Tick functions.
  • The number of draw calls.
  • What the GPU is shading: translucent surfaces, shadows, resolution.

The budget is 11.1 ms. Only the GPU is over it. Reducing draw calls helps the render thread, which is already within budget.

Why is 4× MSAA affordable on Quest when it is expensive on a desktop deferred renderer?

  • Mobile GPUs render in tiles and can resolve multisampling inside the tile before writing to memory, and the forward renderer supports it directly.
  • Quest has a faster GPU than a desktop.
  • It is not affordable; it should be off.

It is also why Mobile HDR stays off: an HDR target changes how the resolve happens and takes the cheap path away.

The game holds 90 Hz for ten minutes, then drops frames. Nothing in the scene changed. What is the likely cause?

  • A memory leak.
  • Thermal throttling: the device lowered its clock speed as it warmed up.
  • The refresh rate was reset by the system.

This is why the store tests for 45 minutes and why you should too. The fix is headroom: a frame that takes 9 ms cold has room to slow down.
