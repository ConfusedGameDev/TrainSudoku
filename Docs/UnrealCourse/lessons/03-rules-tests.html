Legality and the win check

The rule, from Legality.cs:

  • A side is Forced when the neighbour there holds a piece that points back at this cell, or when the side is the S or E tunnel.
  • A side is Forbidden when the neighbour holds a piece that does not point back, or when the side is a board edge with no tunnel.
  • A side is Open when the neighbour is empty.
  • A key is legal when neither of its two sides is Forbidden and it includes every Forced side. Three Forced sides leave no legal key.

Unreal concepts

Automation tests

Unreal's test framework is built into the engine. A test is a C++ class declared with a macro, compiled into your module when WITH_DEV_AUTOMATION_TESTS is on, which it is in editor and development builds and not in shipping builds.

There are two styles. A simple test is one function. An automation spec groups cases with Describe and It, which maps well onto an NUnit fixture: one spec per fixture, one It per [Test]. This course uses specs.

A test's name is a dotted path, such as Tsugi.Core.Legality.TunnelSideIsForced. The path is how you select tests to run.

Owning plain C++ objects

In C#, Board holds a reference to a shared LevelData, and the garbage collector keeps the level alive. Plain C++ objects are not collected in Unreal, so you choose who owns what:

TypeMeaningUsed here for
A valueOwned by whatever contains it; copied on assignmentThe cells array inside a board
TSharedRef<const T>Shared, never null, reference countedThe level a board and its clones all point at
TSharedPtr<T>Shared, may be nullThe solver's first solution, which may not exist
TUniquePtr<T>One ownerThe flow owned by the subsystem, in lesson 5

These are for plain C++ only. Never put a UObject in a TSharedPtr.

Fixed-size and inline containers

Legality.Classify allocates a four-element array on every call in C#. In C++ you can return it on the stack with TStaticArray<T, 4>. Likewise a list that never exceeds six keys can be a TArray<T, TInlineAllocator<6>>, which keeps its storage inside the object. The solver calls these millions of times, so it matters.

Steps

  1. Declare the board. The C# indexer board[x, y] returning Piece? becomes Get returning TOptional. Clone() becomes the copy constructor the compiler writes for you.

    Create a level for a board with MakeShared<FTsugiLevelData>(6, 6), fill it in, then pass it as TSharedRef<const FTsugiLevelData>. Once a board holds it, nobody can change it.

  2. Port legality. This is the file to get exactly right. Compare the two side by side.

  3. Write the test fixtures. Put them in TsugiCore/Private/Tests/. Corridor() is the one most legality tests use: a 3×3 board, entrance west of (0,1), exit east of (2,1), every clue zero.

  4. Port one fixture as a spec. Here are three of the ten legality tests. Port the other seven the same way.

    Check in your engineThe test flag names changed around 5.5 when EAutomationTestFlags became a scoped enum. If EditorContext | ProductFilter does not compile, open Misc/AutomationTest.h in the engine source and copy the flags an engine test uses.

  5. Run the tests. In the editor: Tools > Test Automation, tick the Tsugi group and press Start Tests. From the command line, which is what a build server will use:

    -NullRHI runs without a renderer. The rules tests need no world and no graphics, which is the point of keeping TsugiCore free of the engine.

  6. Port the solver last. It is the longest file and it depends on everything else. Three translation notes:

    • The C# keeps a private nested class Run. Make it a class in the .cpp file's anonymous namespace.
    • int[,] tables become one flat TArray<int32> indexed Y * Width + X.
    • long nodeBudget = long.MaxValue becomes int64 NodeBudget = MAX_int64. SolveResult.First is a board that may not exist: return a TOptional<FTsugiBoard>.

    The search order must stay the same as the C#: cells in row-major order, "leave empty" tried before keys, keys tried in enum order. The order decides how many nodes a search visits, and lesson 4 verifies all 216 shipped levels against the same 5 million node budget the Unity tests use. A different order can push a level over it.

Acceptance checks

  • Every test under Tsugi.Core passes in the editor's Test Automation window.
  • The same tests pass from the command line with -NullRHI.
  • FTsugiSolver::Solve on the Plan Example returns exactly one solution, and it matches PlanExampleSolution from TestLevels.cs cell for cell.
  • The "Lay the solution" button in the demo above shows IsWin: true, and I can explain each of the three conditions from it.
  • The solver reports Exhausted when given a node budget of 10 on the Plan Example.
  • I broke one rule on purpose, saw a test fail, and put it back.

Pitfalls

  • Tests that never appear. A spec only registers when its .cpp is compiled into a loaded module. If the group is missing from the window, check the #if guard and that the file sits under the module's Private/ folder.
  • Deep recursion. The solver recurses once per cell, 64 levels on an 8×8 board. That is fine on PC. Keep the frames small all the same: Android threads have a smaller stack, and lesson 15 runs the solver on the headset.
  • Structured bindings copy. const auto [A, B] = Connections(Key) is a copy of a two-byte struct. Good. Do the same with a board and you copy 64 cells per call.
  • TOptional is not a pointer. Board.Get(x, y) returns a copy. Changing it does not change the board. Write through TryPlace, TryErase or SetUnchecked.

Knowledge check

A cell's north neighbour holds an EW piece. How is the cell's north side classified?

  • Open
  • Forced
  • Forbidden

The neighbour exists and does not point south at this cell, so no key that uses the north side may be placed.

Why does the board hold its level as TSharedRef<const FTsugiLevelData>?

  • Because UObjects must be held in shared pointers.
  • The solver clones boards constantly; the clones share one immutable level instead of copying it.
  • So the garbage collector can find it.

The level is plain C++, so the collector is not involved at all. Reference counting keeps it alive for as long as any board uses it.

A board has a continuous track from S to E, all clues met, and a separate closed loop of four curves elsewhere. Is it a win?

  • Yes.
  • No, extra track is never allowed.

The three conditions are a connected path, exact clues, and no open ends. A closed loop has no open ends. WinCheckerTests has a case for exactly this, using LoopText.
