Signage and maps

The game's interface is two physical things: a signboard standing behind the platform, and a map printed on the platform itself with raised roundels you press. You build both, and the fingertip press that works them, which the Unity edition had to write by hand after the toolkit's own failed.

Unreal concepts

UMG and Slate

Slate is Unreal's C++ UI framework; the editor itself is written in it. UMG wraps Slate in UObjects so widgets can be laid out in a visual designer and driven from Blueprint. You work in UMG.

The pattern that keeps layout in the designer and logic in C++: write a C++ class deriving from UUserWidget, declare the widgets you need as properties marked meta = (BindWidget), then make a Widget Blueprint that derives from it. The designer must contain widgets with those exact names, and the pointers are filled in for you.

Widgets in the world

A UWidgetComponent renders a widget to a texture and draws it on a quad in the level. Its draw size is the widget's size in UI pixels. One pixel is one local unit, so you scale the component to get a real size.

By default it redraws every frame. A sign that changes once a second does not need that. Turn on manual redraw and ask for an update when something changes. On a mobile GPU this matters.

Runtime procedural meshes

The map's strokes depend on which lines are open, so they cannot be baked. A UProceduralMeshComponent takes arrays of vertices, triangles, normals and UVs for a section and draws them. It is the simplest runtime mesh tool, and the map is rebuilt only when the player arrives at it.

The press, and why it is hand-written

Unity's toolkit poke never pressed a button on the headset, and rays were removed. So XRPanelTouch reads fingertip positions and decides for itself. Its rules are worth understanding before you port them, because each one fixed a specific misfire.

RuleValueThe misfire it prevents
A fingertip becomes ready only in front of the panel, between two distances, and over it2 cm to 15 cm; within 2 cm of the panel's edgeA hand arriving from the side or from behind pressing whatever it passes

A second press on the same panel is ignored for a moment0.35 sTracking jitter at the face

A panel can ignore one handThe wrist menu being pressed by the wrist it is worn on

The bug to avoidThe first Unity version compared a fingertip position with button rectangles that were in a different coordinate space, and measured its tolerance in the wrong unit. On the headset every press went to the first button on the page. Everything must be compared in one space: the panel's own UI pixels.

In Unity this logic lives in the engine-bound assembly, mixed with UI calls, and has no tests. In your port, pull the decision out into TsugiCore and test it. This is one place where the port can be better than the original.

Steps

  1. Write the press detector in TsugiCore. It knows nothing about widgets. Each frame it is given fingertips and button rectangles, all already in the panel's pixel space, and answers which button was pressed and which is hovered.

    Write tests for every row of the rules table above before you connect it to a widget. There is no Unity fixture to port; these are new. At minimum: a tip arriving from the side never presses; a slide across the face onto a button does not press; two overlapping-reach buttons give the nearest; the cooldown swallows a second press; the ignored hand presses nothing.

  2. Connect it to a widget component. A small component, UTsugiPanelTouchComponent, sits beside a UWidgetComponent. Each frame it converts fingertips into the panel's pixel space, collects button rectangles in the same space, runs the detector, and clicks.

    Construct the detector with slop and margin converted to pixels: 0.3 / CmPerPixel and 2.0 / CmPerPixel. That conversion is exactly what the first Unity version got wrong.

    Verify on the deviceTwo things here were not confirmed: which way GetLocalHitLocation treats points off the widget's plane, and whether a button's cached geometry inside a widget component is in the same pixel space as the draw size. Draw a debug dot on the widget at each fingertip's computed pixel and outline each button's computed rectangle. Fix the mapping until the dot sits under your finger. Do this before anything else on the sign.

  3. Build the signboard widget. A C++ base class with the bound widgets and one function per view; the layout in WBP_Signboard.

    Station and line names are invented proper nouns and are never translated: wrap them with FText::AsCultureInvariant. Everything else on the sign comes from the string table in lesson 16; use placeholder English until then.

  4. Stand the sign up. An actor, ATsugiSignboard, attached under the board root, with the widget component, two posts and the press component.

    From XRSignboard.csValue
    Panel size in UI pixels1260 × 720
    Width in the room at a 6 cm cell42 cm, so 24 cm tall. Sized in cells, so it scales with the board.

    Set the widget component to manual redraw. Request a redraw when a view is shown, when the clock's displayed second changes, and while the arrival stamp animates.

  5. Port the map rules, then build the map actor. MapFit fits a line's map nodes onto the card. MapStroke turns a line's nodes into a polyline for its shape: a route, a loop or a stadium. MapReveal says which lines the network shows: the open ones, plus the first closed one. Because unlocking is a chain, exactly one padlock is ever on show.

  6. Print the map. The card is 9.6 cells square, about the footprint of an 8×8 board, with its near edge on the board root's origin. On it, flat coloured strokes and raised roundels.

    From the headset checksPrinted layers that share a height fight for depth: a stroke flush with the paper showed only as broken dashes. Each layer floats 0.005 cells above the last, which is 0.3 mm at the standard size.

    Stroke width is a map measurement scaled by the fit, not a fixed size, so lines stay in proportion from two lines to twenty-four. It has a floor of 0.1 cells so the full network's lines do not vanish.

  7. Make roundels pressable. A roundel is a raised disc, 0.12 cells proud of the card. It uses the same idea as the panel press, measured vertically:

    • A fingertip more than 0.25 cells above the face is ready.
    • Coming down to 0.1 cells above the face, over the roundel, presses it once.
    • Coming down to that height off the roundel is a touch-down: it must lift before it can press.
    • Within 0.8 cells it lifts the roundel a little, to show which one you are over.
    • The touch area is 1.4 times the disc's width.
    • A closed roundel answers with a shake and does nothing.

    Reuse FTsugiPanelTouch: treat the card as a panel whose "pixels" are cells and whose "gap" is height above the roundel face, with each roundel a small square button. One tested detector for every press in the game.

Acceptance checks

  • My new Tsugi.Core.PanelTouch tests pass, one for each rule in the table.
  • With debug drawing on, the dot on the sign sits under my fingertip across the whole panel, and each button's outline matches the button.
  • Pressing a sign button with a fingertip works first time, nine times out of ten, with either hand and with a controller tip.
  • Sliding a finger across the sign's face does not press anything.
  • Reaching through the sign from behind does not press anything.
  • The network map shows only open lines plus one closed line with a padlock.
  • Pressing an open line's roundel opens its map; pressing a closed one shakes it.
  • Pressing an open station's roundel starts that station; the map goes and the board appears.
  • No part of the printed map flickers or shows as dashes.
  • The sign faces me from any side of the table and stays readable when I stand over it.

Pitfalls

  • A button acts only in the state that drew it. Unity wraps every button action in When(state, action): a double press must not hit the flow twice. Keep that guard. Your flow would ensure on the second call.
  • A view just shown takes no press at once. When a panel appears under a hand that is already there, call Disarm() so the fingertip must come at it afresh.
  • Widget components and the mobile renderer. A world widget is a translucent, textured quad. Keep the draw size as small as stays legible; 1260×720 is the Unity value, not a law.
  • Text needs the right font. The game's face is Barlow. Import it as a font asset now. Japanese needs a second face added to the same composite font; lesson 16 does that.

Knowledge check

A fingertip approaches the sign from the side, level with its face, and ends on RESUME. Is it a press?

  • Yes, it is on the button at the face.
  • No. It was never ready: it did not pass through the space 2 to 15 cm in front of the panel while over it.

Arming requires coming at the panel from the front. This is what stops a hand working on the board from pressing the sign behind it.

Why move the press decision into TsugiCore when Unity keeps it beside the UI code?

  • UMG cannot run logic.
  • Given tips and rectangles as plain numbers, every rule can be tested without a headset; the space-mixing bug that reached the Unity headset would have failed a test.
  • It runs faster there.

The engine-bound part shrinks to "convert to pixels, call, click", which is small enough to check by eye with a debug overlay.
