Unreal concepts

Names carry a prefix

The prefix is part of the type's name and the build tool checks it on reflected types.

PrefixMeansExample
UDerives from UObject: collected, reflectedUDataAsset
ADerives from AActorAPawn
FA plain struct or classFVector, FString
EAn enumETsugiDirection
TA templateTArray<int32>
IAn interface classITsugiSaveStore
bA bool variablebIsFixed

Reflected types cannot live in a C++ namespace, so this course gives every game type a Tsugi prefix. Free functions can live in a namespace, and that is where C#'s static classes and extension methods go.

Reflection is opt-in

UENUM(), USTRUCT(), UCLASS(), UPROPERTY() and UFUNCTION() are markers. A tool called Unreal Header Tool reads them before the compiler runs and generates a Something.generated.h file that the header must include last.

Mark a type only when the editor, a saved asset or Blueprint has to see it. ETsugiPieceKey is stored in level assets, so it is a UENUM. A piece sitting on a board during play is never saved as an asset, so FTsugiPiece stays plain.

TrapLevel id strings are the save-file identity and they are case-sensitive in the Unity save. Keep them as FString. FName folds case, so two ids that differ only by case would collide.

There are no exceptions

Unreal game code is compiled without C++ exceptions on most platforms. Every throw in the C# becomes one of three things:

  • check(Condition): a programmer error. It stops the program in development builds. Use it where the C# throws for an argument that could only be wrong through a bug, such as PieceKeys.Other asked about a side the key does not have.
  • ensure(Condition): logs a call stack once and carries on. Use it where you can refuse and continue.
  • A bool return with an out parameter: for anything a caller is expected to handle, which the C# already writes as TryX.

Exporting from a module

A class or function that another module calls must be marked with the module's API macro, here TSUGICORE_API. Without it the code compiles and then fails to link from TsugiXR. Functions defined entirely in a header do not need it.

Steps

  1. Port Direction. The enum is reflected. The extension methods become constexpr free functions in a namespace.

    Three things to notice. The enum has an explicit uint8 base, which Blueprint requires. The numeric values are kept, because BoardLayout.Yaw multiplies them by 90 and the save format stores keys by name but the Unity level assets store them by number. And a call that read direction.Opposite() now reads Tsugi::Opposite(Direction).

  2. Port PieceKey. C# returns a tuple from Connections. A two-field struct does the same job and supports structured bindings.

    The name table is written out by hand on purpose. You could ask reflection for an enum's name with StaticEnum<ETsugiPieceKey>(), but these six strings are written into every player's save file. A table that a test pins is safer than a name that changes if someone renames an enumerator.

  3. Port Piece. A plain struct. C#'s IEquatable and GetHashCode become operator== and a free function named GetTypeHash, which is what TMap and TSet look for.

    Where the C# says Piece?, write TOptional<FTsugiPiece>. The board in lesson 3 stores a TArray<TOptional<FTsugiPiece>>.

  4. Port Tunnel and FixedPiece as reflected structs. Level assets store both, so the editor has to see their fields.

    Every UPROPERTY needs a default value in the struct. An uninitialised reflected field is a warning that becomes an error in some build configurations.

  5. Port LevelData. It is a plain class. The data asset in lesson 4 converts to and from it, exactly as LevelDefinition.ToLevelData does in Unity.

    The C# constructor throws when width or height is below one. Use check(InWidth >= 1 && InHeight >= 1): no caller can recover from that. Clone() disappears, because copying a C++ value is the language's default.

Your port

  • Tsugi::TryFromDirections.
  • The three FTsugiTunnel methods, in TsugiTunnel.cpp.
  • FTsugiFixedPiece: a USTRUCT with X, Y and Key, equality and GetTypeHash.
  • All of FTsugiLevelData, including Validate with the same six checks and the same wording. The messages are shown to level authors, and a test in lesson 3 looks for some of them.

Build messages with FString::Printf(TEXT("Column %d clue %d is outside 0..%d."), X, ColumnClues[X], Height) where the C# uses string interpolation.

Acceptance checks

  • The project builds in Development Editor with no warnings from TsugiCore.
  • In the editor, a new Blueprint variable can be given the type Tsugi Piece Key and offers the six keys.
  • FTsugiLevelData::Validate covers clue ranges, clue totals, tunnels on the perimeter, duplicate fixed pieces, fixed pieces pointing off the board or at a piece that does not point back, and fixed pieces exceeding a clue.
  • No file in TsugiCore includes an engine header beyond CoreMinimal.h.
  • I can explain why FTsugiPiece is not a USTRUCT and FTsugiTunnel is.

Pitfalls

  • The generated include must be last. Any #include after X.generated.h is an error from Unreal Header Tool, and the message does not always say so clearly.
  • Missing TSUGICORE_API. The symptom is an unresolved external when TsugiXR or a test links, never a compile error in TsugiCore itself.
  • Header changes and Live Coding. You changed class layouts all lesson. Build from the IDE with the editor closed.
  • TEXT() around every literal. A bare "NS" is a narrow string; FString wants TCHAR.

Knowledge check

Which of these must be a UENUM or USTRUCT?

  • FTsugiPiece, because the board stores it.
  • ETsugiPieceKey, because level assets store it and the editor must display it.
  • FTsugiLevelData, because it is passed between modules.

Reflection is for things the editor, the serializer or Blueprint must see. Crossing a module boundary needs the API macro, not reflection.

PieceKeys.Other(key, direction) throws in C# when the key has no connection towards direction. What is the right Unreal translation?

  • Return North and log a warning.
  • A bool return with an out parameter.
  • checkf: every caller guarantees the precondition, so reaching it is a bug.

PathFinder tests piece.Has(from) before it calls Other. A caller that skips that test is broken, and a silent default would hide the break.

Why keep level ids as FString and not FName?

  • FName cannot contain hyphens.
  • FName comparison ignores case, and the ids are keys in a save file written by case-sensitive code.
  • FString is faster to compare.

FName is the faster one. It is wrong here because of what it does to case.
