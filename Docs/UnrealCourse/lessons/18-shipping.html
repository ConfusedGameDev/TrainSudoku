Shipping to Meta Standalone

A build that runs on your desk is not a build the store accepts. This lesson turns the project into a signed, shipping-configuration APK, checks it against Meta's Virtual Reality Checks one by one, and uploads it to a release channel.

At the end
A signed Shipping APK on a Meta release channel, a completed checklist, and a build you can reproduce from a clean checkout.
On the headset
The game installed from the store's channel, not sideloaded.
Unity equivalent
Milestone XR11, not started. The Unity project's first APK produced a list of store findings; they are the starting point here.

Unreal concepts

Build configurations

ConfigurationContainsUse
DevelopmentLogging, console, checks, automation testsEverything up to now
ShippingNone of those. check is compiled out; ensure no longer reports; console commands are goneWhat you upload

Two things follow. Any debug aid you relied on, such as Tsugi.QuickRails or unlock-all, cannot leak into a Shipping build through the console, but it can leak through a config file, so check the files. And a code path that only worked because a check stopped the bad case will now run the bad case. Play the Shipping build properly before you upload it.

Signing

Android installs an update only if it is signed with the same key as the installed app. The store requires APK signature scheme v2. You create one keystore, keep it and its passwords somewhere safe and backed up, and never commit it to source control. Lose it and you cannot update the app.

The manifest

Unreal generates AndroidManifest.xml from project settings and from each plugin's contribution. Plugins contribute through Unreal Plugin Language files: XML that says what to add to the manifest and the Gradle project. It is the counterpart of the Unity project's post-generate Gradle hook, and it is where you go when a setting has no checkbox.

The Platform window

The Meta XR plugin has a Platform window, opened from its settings page, that uploads a build to a release channel using your app's id and token. It wraps Meta's command-line upload tool.

Steps

  1. Clean out the testing aids. Search the project and every file under Config/:

    • bUnlockAll in the Tsugi settings is false.
    • Tsugi.QuickRails is 0 and is not set in any .ini.
    • Debug drawing of hands and panels is off by default.
    • No per-frame logging remains.
    • The benchmark command does nothing unless asked.

    Wrap debug-only code in #if !UE_BUILD_SHIPPING so it is not in the shipped binary at all.

  2. Create the keystore and sign. Generate a keystore with the JDK's keytool, with a validity of 25 years or more. Put it in Build/Android/ in your working copy and add it to .gitignore. In Project Settings > Platforms > Android > Distribution Signing, enter the keystore file name, the alias and the two passwords.

    Store the keystore and passwords in your team's secret store the same day. A build server injects them at build time; a developer's machine keeps a local copy outside the repository.

  3. Set the packaging options. In Project Settings > Packaging:

    SettingValue
    Build ConfigurationShipping
    For DistributionOn. This is what applies the distribution signing.
    Use Pak FileOn
    List of maps to includeL_Tsugi only
    Localizations to Packageen, ja, es, fr

    In the Android settings: package game data inside the APK, so there is one file and no separate expansion file. Set the final package name. During development you used com.GorillaGonzalez.Tsugi.XR.UE so both builds could sit on one headset; decide with your team what the shipped id is, because it can never change after release.

    Set the version: Store Version is an integer that must rise with every upload; Version Display Name is what people see.

  4. Inspect the manifest you actually ship. Do not trust settings pages. Extract the manifest from the built APK and read it.

    The Unity project's first APK had five manifest findings. Check each against yours:

    ItemRequiredUnity's first APK
    android:installLocationautoWas preferExternal
    uses-feature android.hardware.vr.headtrackingPresent, for an immersive appMissing
    com.oculus.supportedDevicesThe devices you supportWritten as eureka|quest3s; Meta documents quest3. Confirm what the store accepts.
    excludeFromRecents on the launch activityExpected by MetaMissing
    PermissionsOnly what is used: scene, and whatever anchors and hand tracking declareScene permission was once dropped by a package bug

    Meta's plugin writes most of these from its settings page. For anything it does not, add a small Unreal Plugin Language file to your game module and reference it from TsugiXR.Build.cs:

    Not confirmedWhich of the five items plugin 207 already writes correctly was not checked. That is what reading the built manifest is for. The UPL snippet is the standard pattern; verify the element names against an engine plugin's own UPL file before relying on it.

  5. Add the entitlement check. An entitlement check asks Meta's platform whether this user owns the app. Meta recommends doing it within ten seconds of launch. Create the app in the Meta developer dashboard to get an app id, enter it in the Meta platform settings, and in BP_TsugiGameMode's BeginPlay call the platform's verify-entitlement node. On failure, show a message on the signboard and stop the flow from starting.

    A sideloaded build always fails this check. That is expected, and it is in the Unity project's log too. Test the success path with a build installed from a release channel.

  6. Be focus-aware. When the system menu is up, the app is still drawn behind it but must hide its hands and controllers and take no input. You already pause on focus loss. Add: hide the hand visuals and the wrist roundel, and set bAcceptsGrabs false, while unfocused; restore on return. Turn on Focus Aware in the Meta XR mobile settings.

  7. Build it from nothing. A release must not depend on your machine's leftovers. Clone the repository into an empty folder and package from the command line.

    Put that in a script in the repository. It is the answer to the Unity project's note that it has no build script.

  8. Run the tests against the release branch. Every automation test from lessons 3 to 16, from the command line, on the commit you are about to ship. In particular the level test: 216 levels, one solution each, in the order of network.json.

  9. Play the Shipping build. Install the signed APK. With a fresh save: place the board, finish the tutorial, finish a line, unlock the next, quit mid-level and resume, change language, swap hands, take the headset off and on, re-place the board. Then install the next build over it and confirm the save survives.

  10. Upload. Open the Meta XR Platform window from the plugin's settings. Enter the app id and token, choose the ALPHA release channel, point it at the APK, and upload. Invite your team to the channel and have someone who did not build it install it from the store.

  11. Fill in the submission. The dashboard asks for play mode (sitting and standing), input (hands and controllers), a privacy policy URL, age rating answers, and store art. Art has its own checks: no headsets or controllers in images, cover art without extraneous text, a trailer under two minutes.

Your work

  • A release checklist in the repository, RELEASE.md, with one line per check in the table above and who verified it on which build.
  • The build script.
  • The focus-aware behaviour.
  • The entitlement check, with its failure message in all four languages.
  • A note of where the keystore lives, that names a person and not a path.

Acceptance checks

  • A clean clone builds a signed Shipping APK with one command.
  • The built APK's manifest has installLocation auto, the head-tracking feature, the right supported devices, and only the permissions the game uses.
  • The APK is arm64 only and well under 1 GB.
  • All automation tests pass on the release commit.
  • The Shipping build shows passthrough from the first frame, with no black flash, and head-tracked content within four seconds.
  • With the system menu open, hands and the roundel are hidden and nothing in the game responds.
  • An update installed over a played build keeps progress, the board's place and the settings.
  • No testing aid is reachable in the Shipping build: no unlock-all, no quick rails, no console.
  • The build is on a release channel and a teammate installed it from there.
  • The entitlement check passes for that teammate and fails, with a readable message, for a sideloaded copy.
  • RELEASE.md has every applicable check signed off against this build.
  • The keystore is backed up somewhere that is not a developer's laptop, and is not in the repository.

Pitfalls

  • The Shipping build is the first time check is gone. A bug it was hiding will show now. Allow time for it.
  • Debug-signed and release-signed builds cannot update each other. Uninstall the development build before installing the signed one, or the install fails with a signature error that reads like a corrupt file.
  • An asset missing only in Shipping. Usually something loaded by a path string that the cooker never saw. Lesson 4's cook rule covers the levels. Check the cue library, the string table and the fonts the same way: each must be referenced from something that is cooked.
  • Unexplained log lines. The Unity build logs an OpenXR layer-limit error once at every session start, and runs on. If you see the same in Unreal, it is likely the runtime's, not yours. Note it; do not spend a week on it.
  • Changing the package name after upload. You cannot. Decide it in step 3.

Knowledge check

The cue library works in the editor and every cue is silent in the packaged build. What is the most likely reason?

  • Shipping builds strip data assets.
  • Nothing that is cooked references the library, so it was left out of the package.
  • The signing step removed it.

The editor loads anything on disk. A package holds only what is reachable from the maps and the always-cook rules. An asset found by a path string, or assigned nowhere, is not reachable.

Why read the manifest out of the built APK when the settings pages already show what you chose?

  • The settings pages are often out of date.
  • The final manifest is merged from the engine, every plugin and your own additions, and any of them can override or drop an entry.
  • The store requires a copy of it.

The Unity build lost its scene permission exactly this way: three requests from one package overwrote each other during the merge.

You lose the keystore after release. What can you still do?

  • Generate a new one with the same alias and passwords.
  • Ask Android to reset it.
  • Nothing that updates the installed app. A new key is a different signer.

A keystore's identity is its private key, not its name. This is why it is backed up on day one.

The end of the line

You have ported a rules engine with its tests, built a data pipeline, learned the game framework, put actors and components in a room, written your own hand interaction, drawn UI in the world, localised it, measured it and shipped it. That is most of what day-to-day Unreal work is.

Two things to do before you close this course. Go back through the yellow boxes: each is a place where this course could not confirm something and you now know the answer. Send those answers, and every snippet you had to fix, to whoever maintains the course. And tell the owners of the Unity edition what you found on the headset for the tutorial and for sound and language, which they had not yet verified. You are now the team that has.
